Compiler vos commandes : du prompt au script

Une commande, un skill ou un agent écrit en prompts peut être compilé : ses étapes répétables deviennent des scripts testés et partagés, et sa part automatisée est mesurée avant et après.

Installer

L’équipe de Camille a écrit deux commandes pour son assistant : /release-notes et /publish-docs. Les deux fonctionnent. Mais les deux demandent à un modèle de vérifier les mêmes liens, à chaque fois, au prix de jetons et avec des résultats qui varient d’une exécution à l’autre. Elle se demande quelles étapes ont vraiment besoin d’un modèle, et si les autres pourraient être figées une fois pour toutes.

L’idée en une image

Le métier a plusieurs noms pour ce passage. On parle d’IA compilée ou de distillation de workflow quand la logique d’un prompt est figée dans du code ordinaire, qui s’exécute toujours de la même façon, sans coût de modèle. DSPy emploie d’ailleurs le mot : il compile des appels de modèle déclaratifs en chaînes optimisées.

Quand un modèle reste dans la boucle, le décodage contraint garde sa réponse exploitable par un script. Claude et OpenAI proposent tous deux des sorties structurées qui suivent un schéma JSON ; GenAIScript écrit les prompts en JavaScript.

AI-KIDO applique cette idée à ce que vous écrivez déjà : commandes, skills et agents. Chaque étape entre dans l’une de trois classes, et la part automatisée est leur moyenne pondérée.

  • Déterministe · 1Un script ou une commande écrite dans l’étape. Même entrée, même sortie, aucun modèle.
  • Assistée · 0,5Un modèle qui doit renvoyer un schéma de sortie validé. Il écrit toujours, mais un script peut le vérifier.
  • Ouverte · 0Un prompt libre, une décision humaine, ou une règle que l’agent doit respecter. Précieuse, mais pas un script.

Ce que fait Camille : compiler deux commandes

Dans Tatami, elle demande de compiler les deux commandes d’un coup. Le compilateur découpe chaque définition en étapes et les classe. Pour les étapes ouvertes, un modèle propose une commande ; le compilateur vérifie ensuite le résultat avant de l’accepter, et l’équipe relit le changement comme n’importe quel autre.

  1. Vous
    Compile /release-notes et /publish-docs.
  2. Assistant
    Les deux sont compilées, version 1.0.0 → 1.0.1.
    /release-notes : 0 → 0,5. La vérification des liens et le comptage des pull requests tournent désormais en scripts ; la rédaction et la relecture restent au modèle et au mainteneur.
    /publish-docs : 0,33 → 0,67.
    3 scripts générés, 1 partagé : la vérification des liens est la même dans les deux commandes, elles appellent donc le même script.

Elle ouvre /release-notes. Rien n’a disparu : chaque étape garde sa phrase, et celles devenues scripts disent maintenant lequel elles appellent.

Chaque script généré rejoue exactement la commande qu’il remplace, peut l’afficher sans l’exécuter (--print) et vient avec son test. Son nom porte une empreinte de la commande : deux définitions qui font la même chose finissent par appeler le même script.

Ce que montre le score, jusqu’à l’agent

L’agent de release de l’équipe fait peu de choses lui-même : il choisit le numéro de version avec les mainteneurs, puis appelle les deux commandes. Sa part automatisée est la moyenne de ses propres étapes et de ce qu’il appelle. Elle monte donc sans que personne ne le touche.

À retenir

Une compilation est refusée si elle change le nombre d’étapes, si un script ne rejoue pas la commande d’origine, ou si la part automatisée baisse. La version ne monte que si la compilation est acceptée.

Sur les commandes d’AI-KIDO lui-même

Nous avons passé dix commandes publiques de la version 1.5.5 au compilateur. Neuf ont été compilées en onze scripts. /aikido-review a été refusée, à juste titre : elle n’a aucune étape qu’un script peut exécuter, car relire sur preuves est un jugement.

  • 9/10commandes publiques 1.5.5 compilées
  • 11scripts générés, chacun avec son test
  • 0score modifié : leurs commandes étaient déjà écrites comme des commandes

Les scores n’ont pas bougé, et c’est instructif. Beaucoup d’étapes ouvertes de ces commandes sont des garde-fous, comme « Ne modifier aucun fichier sauf demande de l’utilisateur ». Aucun script ne remplace une règle de conduite ; le but n’est pas 100 %, mais de ne plus payer un modèle pour ce qu’une commande fait exactement.

Et pour les workflows

Les workflows ont leur propre score, /workflow-score, qui classe chaque état. Sur le workflow des notes de version de notre article 1.5.5, faire de la vérification des liens un script et donner un schéma de sortie à la rédaction le fait passer de 0,25 à 0,63, la relecture humaine restant ouverte exprès.

Deux règles derrière le compilateur

La version 1.5.5 ajoute deux points durs que suit chaque agent AI-KIDO. Code Economy fait s’arrêter l’agent sur la route la moins chère : une commande ou un script existant avant du code neuf, et c’est pourquoi le compilateur réutilise un script partagé plutôt que d’en écrire un second.

Agent Economy traite les jetons et les nouvelles tentatives comme un budget, et un appel en échec ne prouve rien. Si le script des liens dépasse son délai, l’étape est signalée non vérifiée, jamais « aucun lien cassé ». Pour le principe général, lisez notre article sur les outils déterministes.

Essayer

  1. Installez la CLI 1.5.5 : npm install -g @aikido-method/cli@1.5.5, ou suivez la page d’installation.
  2. Dans vos commandes et vos skills, écrivez les étapes répétables comme de vraies commandes entre accents graves : elles sont déterministes dès le départ.
  3. Avec un Tatami Core Agent configuré (aperçu de développement), compilez vos commandes, skills ou agents, puis comparez la part automatisée avant et après.
