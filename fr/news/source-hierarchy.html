Greenfield ou legacy : qui fait foi, la spec ou le code ?

Les approches spec-driven sont taillées pour le neuf, celles qui partent du code pour l’existant. AI-KIDO tente de réconcilier les deux : son évaluateur choisit la source qui fait foi selon votre demande.

Vous arrivez sur un monolithe de quinze ans. Le dossier docs/ décrit une application qui n’existe plus, et le seul document fidèle, c’est le code. Le lendemain, vous démarrez un produit de zéro : pas une ligne de code, et toute la vérité tient dans ce que vous allez écrire. Dans les deux cas, vous demandez à un assistant de coder. Dans les deux cas, il doit savoir à quoi se fier. Et ce n’est pas la même chose.

Cet article pose une question simple : quand on travaille avec des agents, qui fait foi, la spécification ou le code ? Il montre pourquoi les approches courantes répondent bien à un seul des deux cas, puis comment AI-KIDO essaie de faire la part des choses en regardant, à chaque demande, d’où vous partez et ce que vous voulez faire.

Quatre situations, quatre vérités

Avant de parler d’outils, distinguons ce que vous vivez réellement sur un projet.

  • Projet neuf (greenfield)Rien n’existe. La spécification est la seule trace de l’intention : c’est elle qui doit faire foi.
  • Transformation d’un existantVous modernisez ou déplacez un système qui fonctionne. L’ancien comportement et la cible comptent tous deux : deux vérités à la fois.
  • Maintien d’un code legacyVous corrigez, ajoutez, comprenez. Le code en production est la réalité ; la documentation, elle, a peut-être vieilli.
  • Cas mixtesUne nouvelle fonctionnalité dans un vieux système, une API externe à brancher : la source qui mène change avec la demande.

Retenez cette idée, elle porte tout le reste : la même source est tantôt la vérité, tantôt du bruit, selon ce que vous faites. Un README est précieux pour concevoir un nouveau module, et trompeur pour comprendre un bug en production.

Quand la spécification fait foi

Le spec-driven development (SDD) renverse l’ordre habituel : on écrit d’abord ce que le logiciel doit faire, puis l’agent produit le code. GitHub présente ainsi Spec Kit : la spec est un contrat sur le comportement attendu, et elle devient la source de vérité que les outils et les agents utilisent pour générer, tester et valider le code.

Le travail avance par phases, avec des points de contrôle. On décrit d’abord le quoi et le pourquoi (Specify), puis on fournit la pile technique, l’architecture et les contraintes (Plan). GitHub précise que c’est dans cette phase de plan que l’on signale une intégration avec l’existant ou une exigence de conformité.

Kiro, l’éditeur d’AWS, organise lui aussi le travail en trois phases : exigences (requirements.md), conception (design.md) et tâches (tasks.md). Sa documentation prévoit aussi des specs de correction de bug, qui décrivent le comportement actuel, le comportement attendu et ce qui ne doit pas changer.

Le Technology Radar de Thoughtworks résume le mouvement : une approche émergente du code assisté par IA, encore en cours de définition, où l’on part d’une spécification fonctionnelle structurée avant de la découper en solutions et en tâches. Le Radar cite Kiro et Spec Kit, dont la constitution fixe des principes immuables, puis place Tessl du côté le plus radical : la spec y prend le pas sur le code.

Trois niveaux de rigueur

Tous ces outils ne demandent pas le même engagement envers la spec. Birgitta Böckeler (Thoughtworks), dans une série publiée sur le site de Martin Fowler, distingue trois niveaux.

Böckeler observe que toutes les approches qu’elle a examinées sont spec-first, mais que toutes ne cherchent pas à garder la spec vivante, ni à en faire la source unique.

Une prépublication arXiv de Deepak Babu Piskala décrit les mêmes trois niveaux et propose un cadre pour décider quand le SDD apporte de la valeur et quand une approche plus simple suffit. C’est une prépublication, pas encore une étude évaluée par des pairs.

Pour un produit neuf, ce modèle est naturel. Vous démarrez de zéro, il n’y a pas de code qui contredise la spec, et chaque décision peut être écrite avant d’être codée. La spec est la vérité, le code en est l’aboutissement.

Quand le code fait foi

Sur un système ancien, l’exercice est inverse. Les spécifications d’origine ont été modifiées par vingt mains, la documentation a vieilli, et ce qui tourne en production est la seule description exacte du comportement. Le principe « le code est la source de vérité » n’a rien de neuf : il guide depuis longtemps ceux qui travaillent sur de l’existant. Ce que l’IA change, c’est la vitesse à laquelle on peut le lire.

Les auteurs de Thoughtworks font ce constat dans un article publié sur le site de Martin Fowler en septembre 2024 : la plupart des usages de l’IA générative en développement visent à produire du code, alors qu’il y a autant de valeur, sinon plus, à comprendre le code existant, surtout dans les systèmes anciens, gros et complexes.

Leur outil, CodeConcise, associe un modèle de langage à un graphe de connaissances construit à partir des arbres syntaxiques du code. Ils rapportent de bons résultats pour en tirer des exigences de bas niveau et une explication de haut niveau du système. Autrement dit, on part du code, et c’est lui qui nourrit la documentation.

Les grands acteurs du cloud proposent des offres dans cette direction. AWS Transform se présente comme un service agentique qui vise à accélérer et à sécuriser chaque étape de la modernisation : infrastructure, applications comme le mainframe ou Windows, et correction continue de la dette technique.

Microsoft décrit GitHub Copilot modernization comme une solution agentique de bout en bout qui analyse et met à niveau des applications Java, .NET et C++, et aide à migrer certaines d’entre elles vers Azure. Dans les deux cas, le point de départ est l’application telle qu’elle existe aujourd’hui.

Des habitudes qui ont fait leurs preuves

Ces outils s’appuient sur des pratiques bien antérieures. Dans Working Effectively with Legacy Code, Michael Feathers propose des stratégies pour travailler avec de grandes bases de code sans tests.

Martin Fowler rappelle qu’une couture (seam) est un endroit où l’on peut changer le comportement du système sans toucher à son code source. On s’en sert pour casser des dépendances, tester plus simplement, insérer des sondes d’observabilité ou rediriger le flux vers de nouveaux modules ; il attribue le terme à Michael Feathers.

Le même auteur décrit le Strangler Fig, terme aujourd’hui courant pour une approche graduelle de la modernisation : l’ancien système est remplacé peu à peu plutôt que d’un seul coup.

Côté documentation, Cyrille Martraire défend dans Living Documentation l’idée que l’on n’a pas à choisir entre un logiciel qui fonctionne et une documentation complète : une documentation vivante peut aider à tous les stades d’un projet.

2 famillesd’approches, chacune experte d’un seul point de vue : la spec pour le neuf, le code pour l’existant

Pourquoi chaque famille voit un seul côté

Il n’y a là aucun défaut, seulement une spécialisation. Une approche spec-driven suppose qu’une spec bien pensée précède le code ; sur un projet neuf, c’est vrai. Une approche centrée sur le code suppose que le comportement réel est la référence ; sur un système ancien, c’est vrai aussi. Le problème apparaît quand le terrain mélange les deux. Vous ajoutez une fonctionnalité dans un vieux système : faut-il écrire une spec complète, comme pour un produit neuf, ou plutôt lire le code autour ? Vous corrigez un bug dans un module récent, à côté d’un module hérité : la spec du nouveau module suffit-elle ?

Dans les sources que j’ai lues, chacune de ces familles est décrite par son propre point de départ. Je n’y ai pas trouvé d’outil présenté comme un arbitre qui, pour chaque demande, choisit entre la spec et le code. C’est cette lacune qu’AI-KIDO tente de combler, sans prétendre à l’exhaustivité sur le marché : je n’ai lu que les sources citées ici.

AI-KIDO : laisser la demande décider

AI-KIDO ne choisit pas un camp. Son agent agent-aikido-truth-evaluator a une mission formulée ainsi dans sa définition : déterminer ce qui représente la « vérité » selon le scénario de développement. Pour du spec-driven (une nouvelle fonctionnalité), les specs font foi. Pour de la maintenance (du code existant), l’implémentation fait foi. En cas de conflit, c’est le contexte qui tranche. Son rôle est celui d’un arbitre : il dit à quelle source se fier, il ne décide pas de ce qu’il faut faire ensuite.

Huit scénarios, une source principale pour chacun

L’évaluateur range votre demande dans l’un des huit scénarios de sa matrice, à partir des mots que vous employez. Voici ce que dit cette matrice, côté source principale :

La spec ou la cible mène

  • Nouvelle fonctionnalité (« implement », « add ») : les specs de gen/ et de hard_points/.
  • Démarrage de zéro (« initialize », « bootstrap ») : les specs du projet.
  • Configuration : les specs de configuration des points durs.
  • Intégration d’API : la documentation officielle de l’API externe.

Le code mène

  • Correction de bug (« fix », « bug ») : le code actuel, avec les tests en appui.
  • Documentation (« document », « README ») : le code actuel, c’est-à-dire la réalité.
  • Investigation (« understand », « how does ») : l’implémentation, avec les tests et l’historique Git.
  • Refactoring : à la fois les objectifs et le code actuel, deux vérités.

Regardez le cas du scénario « Documentation » : c’est le code qui mène, et les specs ne viennent qu’en référence pour l’intention. C’est exactement l’idée du « code as truth » appliquée à l’écriture de documentation. À l’opposé, pour une nouvelle fonctionnalité, ce sont les specs qui mènent et le code existant n’est pas à suivre, sauf s’il est cité. Les deux familles de l’industrie cohabitent donc dans une même table, et c’est votre demande qui sélectionne la ligne.

La hiérarchie des emplacements

Au-dessus de ces scénarios, AI-KIDO fixe un ordre entre les emplacements de la connaissance : hard_points/ (les vérités immuables, priorité absolue), puis gen/ (les tables de vérité du projet, qui évoluent), puis le code, la documentation et la configuration. Le dossier spec/, votre espace personnel, n’est jamais une source de vérité : il est ignoré sauf si vous l’activez explicitement.

Les conflits, un signal plutôt qu’un incident

Quand deux sources se contredisent, l’évaluateur ne tranche pas en silence. Si gen/ et le code ont divergé, il signale un conflit à traiter en priorité et recommande de les réaligner. Si toutes les sources sont périmées, il signale de la dette technique et recommande d’enquêter d’abord. Si la situation tourne en rond, il renvoie la décision à l’humain avec son analyse. Chaque source reçoit une note qui tient compte du scénario, de l’emplacement, de la fraîcheur et de la présence de tests (des bonus), ainsi que d’une mention « déprécié » ou d’une contradiction avec une autre source (des malus).

À retenir

L’évaluateur reste un arbitre. Il classe les sources et signale les contradictions ; il ne décide jamais de l’implémentation. Le choix de la correction reste le vôtre et celui de votre agent.

Ce que vous faites, ce que vous voyez

Reprenons le cas du monolithe. Vous devez corriger un bug dans un module d’authentification ancien. Avant de laisser l’agent modifier quoi que ce soit, vous lui demandez de lancer l’évaluateur :

  1. Vous
    Je dois corriger un bug de connexion dans le module d’authentification. Lance l’évaluateur de vérité : quelles sources dois-je croire ?
  2. Assistant
    Truth Evaluation : correction de bug
    🥇 Source principale : le code actuel du module (confiance élevée).
    🥈 En appui : les tests, qui disent le comportement attendu.
    🥉 En référence : les specs de gen/, pour l’intention.
    ⚠️ Conflit : la table de vérité décrit un flux que le code n’applique plus.
    ❌ À ignorer : tout ce qui se trouve dans spec/.

Ce que vous lisez ressemble à un classement. Cet exemple est illustratif : le contenu réel dépend de votre projet, mais la forme est celle que définit l’agent, avec la source principale, les sources d’appui, les conflits, ce qu’il faut ignorer, puis une recommandation et un niveau de confiance. Vous décidez ensuite : le code a raison, la table de vérité est à mettre à jour, ou l’inverse.

Maintenant, l’autre journée : vous démarrez le produit neuf et vous demandez « implémente la connexion par e-mail ». Le même évaluateur classe cette fois la demande comme une nouvelle fonctionnalité. Les specs mènent, l’architecture appuie, et le code existant n’est pas une source à suivre, sauf s’il est cité. Vous n’avez rien changé à votre façon de demander : c’est la formulation de la demande qui a orienté le classement.

Garder les sources d’accord : check-truth

L’évaluateur répond à une demande. La commande /check-truth s’occupe de l’ensemble : elle vérifie la cohérence entre la documentation de la Memory Bank et le code du projet, détecte l’obsolescence et les conflits, et propose une remédiation automatique. Vous pouvez la lancer sur tout le projet, ou la restreindre avec des options.

Pour aller vite, la commande s’appuie sur l’en-tête de chaque document : s’il porte une date de dernière vérification, un statut à jour et des sources inchangées, la vérification est sautée. Le fichier de l’agent donne cet exemple d’en-tête.

Au bout du compte, vous obtenez un rapport lisible : les fichiers cohérents, les écarts mineurs, les conflits majeurs, puis des actions recommandées. La correction automatique, elle, n’a lieu que si vous la choisissez.

Un schéma pour garder en tête

Ce que cette approche apporte, c’est surtout de la souplesse. Elle ne vous demande pas de choisir une religion une fois pour toutes. Elle accepte que, dans la même semaine, la spec soit la vérité le lundi et le code le mercredi, et elle vous aide à ne pas les confondre.

À essayer

  1. Choisissez une vraie demande en cours, par exemple un bug ou une nouvelle fonctionnalité.
  2. Demandez à votre assistant de lancer l’évaluateur de vérité avant de modifier quoi que ce soit, en reprenant le mot de votre demande (« corriger », « implémenter », « comprendre »).
  3. Lisez le classement, suivez d’abord la source principale, puis traitez les conflits signalés en mettant à jour la Memory Bank ou le code.
