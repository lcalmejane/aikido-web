AI-KIDO in practice · Harness creation

Build your tailored AI harness. Evolve it as your needs change.

A harness gathers everything that frames AI on a task: context, roles, workflow, tools, checks. AI-KIDO helps you build it, block by block.

Discover the creation tools What is a harness? See a practical example

What is a harness, and why does it matter?

On its own, a model knows neither your project nor your rules. The harness is what surrounds it so it completes a task reliably.

Without a harness

A capable but unpredictable assistant

You re-explain the context in every session, results depend on how each person phrases the prompt, and nothing guarantees that your rules are applied.

With a harness

A framed, repeatable way of working

The assistant knows where to find the knowledge, which role to take, which workflow to follow and what to verify. The same task produces consistent results, whoever starts it.

With the AI-KIDO meta-harness

A harness for each need, built on demand

Instead of a single fixed harness, AI-KIDO provides the tools to create, combine and improve harnesses from your Memory Bank, for development, documentation, review or any recurring task.

What a harness is made of, and what AI-KIDO provides

  • Context · the Memory Bank: one entry point, structured knowledge loaded only when needed.
  • Roles · personas and agents with a defined expertise, scope and instructions.
  • Workflow · commands that make the steps explicit and reusable.
  • Capabilities · skills, and executable tools connected through your assistant or MCP.
  • Checks · hard points and maintenance agents that validate, rebalance and index the knowledge.

Example · Product communication

A product page to prepare every week? Build your own publishing harness.

One way to combine the blocks. Your sources and guidelines stay in the Memory Bank; the harness defines how to use them.

  1. Create

    Define a product-copywriter persona, a brand-voice skill and a command for reviewing sources, drafting and checking claims.

  2. Use

    Your assistant follows the workflow using the product knowledge in the Memory Bank. Your team approves the claims before publication.

  3. Improve

    Add a reviewer agent, refine the command after feedback and keep the validated workflow as a use case for the next product.

Your harness is a starting point, not a fixed product.

Add a persona, refine an agent, extend a skill or create a command. Test on real tasks, then keep what works.

Optimize commands without changing their purpose

Executable tools connect through your assistant or MCP, including Kimono; creating a skill does not connect a service by itself. The maintenance agents keep the base organized; your team approves domain results.

Principles · Deterministic tools

Don't ask the model to do what a script can do exactly.

A harness is not only prompts. The most reliable harnesses hand every exact, repeatable step to a deterministic tool, and keep the model for understanding, choosing and judging. The result is more dependable, and it costs far fewer tokens.

Left to the model

Every step is paid in tokens

Reading hundreds of files to rename a term, comparing values, rewriting each file, then checking the result: every pass is billed as input and output, and every pass can slip. The longer the job, the more the pile wobbles.

Run by a script

One command, one short answer

The script scans, changes and counts. The model reads a few lines of JSON, such as how many files changed and which ones failed, and decides what comes next. Its context stays small, so every next step stays quick and cheap.

Commands and agents that build tools

Each new command adds a tool to the harness

When you create a command or compile an agent, AI-KIDO separates what needs judgement from what has an exact answer, and asks for the exact part as a dependency-free Node.js script. Every later command and agent can reuse it, so the toolbox grows with your harness.

What it changes for reliability and for cost

  • Reliability. A script gives the same answer for the same input, on every run. It can be tested like any code, it prints a bounded JSON result, and it fails with a clear error and a nonzero exit code instead of claiming success. The tools that write files plan first, then apply, and keep a way back.
  • Token cost (TCO). You pay tokens to read, decide, write and correct. A script replaces that loop with one call and a short report, so there are fewer passes, fewer retries and a smaller context to carry through a long session. The same step also costs the same every time, which makes the bill easier to predict.
  • Auditability. A plan, a dry run and a report can be replayed and reviewed by your team. A reasoning chain buried in a conversation cannot.

AI-KIDO's deterministic principles

Principle 1

The model talks and decides

It understands the request, asks the right questions, picks a route and judges what no rule can settle.

Principle 2

The tool executes

Anything with an exact answer runs in a script. By default AI-KIDO writes it in Node.js 24+ (.mjs), with no dependency, one JSON object on output and tests run by node --test. See the tooling standard.

Principle 3

The cheapest deterministic route comes first

An existing tool, then a generic engine, then a temporary script. A direct edit by the model is kept for a few files or for changes that need judgement.

Principle 4

The limits stay visible

A tool cannot tell whether an image is right or a claim is true. That part goes back to a reader and to your team, and the report says what was checked and what was not.

Refactoring agents: build the tool, then run it

Changing a name across 200 files is the textbook case for burning tokens. The AI-KIDO refactoring agent follows a rule: compare the routes before touching anything, then take the cheapest deterministic one.

RouteUse it when
1 · An existing toolA formatter, a codemod, --fix from a linter or a project script already does the job.
2 · The generic engineThe same literal or regular-expression replacement applies everywhere. The engine runs scan, plan, apply --dry-run, then apply, and rollback if the project's checks fail.
3 · A temporary scriptThe rule needs logic (a move, a condition per file) but stays deterministic. The agent creates the script, runs it as a dry run, applies it, runs it again to prove it changes nothing the second time, then deletes it. It is never committed.
4 · A direct editOne to three files, or when each change needs judgement.

When the work is too large for one context, the agent splits it into wide batches (40 files or 400 KB by default). A batch that needs judgement goes to one sub-agent with exclusive ownership of its files, and only then. Everyone answers with a few lines instead of file lists, logs or diffs:

{"route":"engine","scope":"src/**/*.ts","files":212,"batches":6,"applied":212,"remaining":0,"failed":[],"checks":"ok"}

These are the benefits we expect from the approach, and the refactoring agent is told not to claim savings it has not measured. The only measured token figures on this site come from the Kimono benchmark, on two research tasks; they are not a measured reduction of the full TCO. The illustrations in this section were generated locally with Local Designer, which follows the same split: scripts check the brief, the lock and the colours, and a reader looks at every image.

Where a script can decide, it decides. Where it cannot, someone reads and says so.

That split keeps the model's tokens for what needs them, and gives your team results it can trust and check.
