Privacy · Data control · Zero Trust

Index your knowledge without sending it to a remote LLM

Extraction, chunking and embedding computation run on the Kimono RAG MCP host: your workstation or the server you choose. During indexing, no data seen by the server is sent to a remote LLM or embedding API. Its embedding models run locally; they are not remote generative assistants. The server audits the CPU and GPU usage available on the host and sizes itself to it, so MCP tools run at the best measured speed without changing where the data lives.

Local processing

Keep control of your corpus

Code, documents and vector representations are processed on the server host. Initial model downloads are a separate operation requiring confirmation; they do not send the documents being indexed to the model provider.

Resource budgets

Size indexing for the machine

The engine evaluates available CPU and memory resources to size its workers, threads and batches within configured budgets. For ONNX models, automatic selection compares available CPU and accelerated providers, including CUDA or Core ML depending on the host, and selects the measured fastest option. A GPU is not assumed to be faster.

Context consumption

Choose where your assistant runs too

Local indexing and the assistant’s response are separate stages. Passages read through MCP may be sent to that assistant’s model. If third-party disclosure is prohibited, use a local model or controlled private infrastructure too, with a client configured accordingly.

Useful context within an explicit trust boundary

This separation helps minimize exposed data: the corpus is indexed locally, then only requested passages are provided to the MCP client. It follows the market’s expected practices for Zero Trust and non-disclosure to third parties: data minimization, least privilege, no third-party flow during indexing. It does not by itself constitute Zero Trust certification. Authentication, authorization, isolation, file access and network egress controls still need to be established in your deployment.

For the consumption stage, one choice remains: the model that reads the retrieved passages. A Zero Data Retention (ZDR) LLM service, or another sovereign or private solution on the market, lets you meet the strictest expectations, depending on the features and terms actually covered. A ZDR service still receives the data sent to it: ZDR means neither no third-party transmission nor sovereignty. For a sovereign or private solution, also verify hosting, operators, jurisdiction, logs, backups and subprocessors, along with your organization’s applicable obligations.

Use cases where code must not be disclosed

The contexts in which clients most often require this guarantee:

  • R&D and intellectual property: proprietary code, algorithms, prototypes, pending patents and trade secrets.
  • Software vendors and embedded or industrial systems: product source code, firmware, protocols and differentiating know-how.
  • Service providers and multi-client teams: repositories under NDA, segregated case files and contractual confidentiality commitments.
  • Healthcare, finance and insurance: sensitive documents and data, subject to minimization, access controls and sector-specific requirements.
  • Legal, audit and strategic operations: contracts, confidential cases, internal analysis and mergers and acquisitions.
  • Security, compliance and pre-release code: unpublished fixes, vulnerability analysis, audit findings and secrets inventories.
  • Personal data and regulated data: code and documents that process customer, employee or user data under privacy law.
  • Public sector, defense and critical infrastructure: restricted-access environments, residency requirements or isolated networks after provisioning the required components.

References: NIST Zero Trust principles · example ZDR terms and scope. Choosing Kimono alone does not establish regulatory compliance or sector-specific accreditation.

All Tree-sitter languages and parsers

Version 0.9.9 upgrades Tree-sitter from 0.25.10 to 0.27.2. The registry contains 24 official grammars and 169 compatible third-party grammar crates, covering 174 additional languages. Four GPL/LGPL-licensed grammars are excluded from the MIT binary. The complete, versioned Tree-sitter registry tree-sitter-grammars.json lists every compatible crate.

Instead of splitting every source file at an arbitrary line count, Kimono RAG MCP can split many languages around syntax definitions. It also recognizes top-level JSON keys and JSDoc @typedef, @callback and @interface blocks. That gives search smaller code passages with their structure intact.

Files whose content cannot be indexed, including non-text files, remain represented by their metadata: name, path, extension, size and modification date. Their presence can therefore be found without indexing their binary content. Ignore rules and configured size limits still apply.

The nine embeddings and custom mode

The nine embedding models

These are the nine catalogue choices. Each card shows the selectable ID, local engine and vector dimension. Language profiles describe embeddings, not the Tree-sitter grammars above. Profiles come from the versioned catalogue embedding-models.ts.

  • Potion Code 16M v2code · Model2Vec · 256 dimensions. Code; English; static embeddings for fast local indexing.
  • Potion Multilingual 128Mmultilingual-fast · Model2Vec · 256 dimensions. Multilingual documents; static embeddings.
  • Multilingual E5 smalle5 · ONNX · 384 dimensions. Multilingual documents; contextual model supplied in the host bundle.
  • Jina v2 base codejina-code · ONNX · 768 dimensions. Code; catalogue describes 30 programming languages and English text.
  • BGE-M3bge-m3 · ONNX · 1 024 dimensions. Code and documents; multilingual.

What custom mode lets you do

In the model-management panel, choose custom instead of an automatic policy. Two independent pickers let you select one catalogue model for code and another for documents. For example: Jina v2 base code for source files and Multilingual E5 large for documentation. This is a configuration choice, not a measured performance claim.

  1. Compare profiles: code or document use, language, download size, license and estimated memory. Inspecting status never triggers a download.
  2. Select the code and document models independently from the nine pinned catalogue entries. Custom mode does not load an arbitrary model or URL.
  3. Explicitly approve any required downloads. Revisions, sizes and SHA-256 checksums are verified; the corpus is not sent to an external embedding API.
  4. Confirm the configuration. Kimono RAG MCP partitions files by content type, rebuilds the index in the background and activates the new generation only after success. Missing models are reported, not silently substituted.
  5. Track requested and active policies. If rebuilding fails, the previous index stays available; existing snapshots retain their selection. Vectors from different models stay separate and search results are fused by rank.

auto-speed remains the default policy in 0.9.9; custom gives you control over that model pair. If the corpus contains only code or only documents, only the matching profile is used. Embeddings are computed locally; passages returned to chat may subsequently be sent to your assistant’s model provider.

Downloaded ONNX models now receive only the inputs their model graph declares. That avoids sending unsupported inputs to XLM-R models, while the bundled E5 model keeps its existing path.

Snapshots, multiple searches and delegated agents

A project question can cross source code, documentation and nested repositories. When an assistant delegates those checks, each agent needs to search the same project state. Kimono RAG MCP server 0.9.9 improves that retrieval layer: it helps an orchestrator share one snapshot, but it does not create or coordinate agents.

Ask once, then let the task fan out

In an MCP-capable chat, ask for a concrete investigation. If the assistant supports delegated work, tell it to keep those searches on the same Kimono RAG MCP snapshot:

One freeze for the swarm, not one per search

The orchestrator calls begin once to freeze the relevant corpus, then passes the returned snapshotId to its delegated agents. The code agent can run several searches and read selected functions while the documentation agent checks the written rules against that same snapshot. Every aikido_search and aikido_file request reuses the shared ID: neither a new question nor a new agent requires its own freeze.

The optimization is shared preparation: one captured corpus instead of separate captures for every search or agent, fewer lifecycle calls, and one consistent project state for comparing their findings. Agents retrieve only their own relevant passages; sharing a snapshot does not mean sending the whole corpus to each model. Independent queries can also be grouped in one search request, and selected file ranges in one read request. The Kimono RAG MCP retrieval guide MCP retrieval reference documents these operations.

Once all delegated searches and reads have finished, the orchestrator calls end once for the shared snapshot. Agents do not each release it after their own search. The task therefore follows one freeze → several agents, searches and reads → one end, not a complete freeze/search/read/end cycle repeated for every search.

In 0.9.9, the default prompt scope can also reuse a live snapshot on a subsequent begin for the same user, owner and paths while the corpus is unchanged. Explicitly passing the existing ID keeps delegated work on the captured state even if source files change meanwhile. session keeps a view for the server session; call closes it immediately on end. To inspect edits, start a new capture; fresh: true forces one.

Calling end releases a snapshot; released ones close after 120 seconds idle. A snapshot's sliding lifetime tops out at one hour. At the default limit of eight active snapshots or the byte budget, Kimono RAG MCP evicts released snapshots first.

Multi-repository accounting and reliable indexing

Corpus status now accounts for Git-kept files in each repository. Excluded directories, temporary files and environment templates can be counted as metadata only; Git-tracked files remain indexed even when a .gitignore rule matches, and .git/info/exclude is honored. The report explains metadata-only files. On modified trees, Kimono RAG MCP can reuse vectors for unchanged documents. When you change the embedding policy during an indexing run, Kimono RAG MCP stops that run instead of refusing the change. Server shutdown cancels indexing cleanly, releases its locks and keeps the previous generation unless the new one completed successfully.

Indexable documents and data

Text files are read directly; they do not need an office document extractor. The default RAG corpus includes:

  • Notes and documentation: .md, .mdx, .mdc, .txt, .rst, .adoc, .tex, .bib, .rmd, plus extensionless README, LICENSE, NOTICE and CHANGELOG files.
  • Data and interchange: .csv, .tsv, .json, .jsonc, .json5, .xml, .yaml, .yml, .toml.
  • Configuration and schemas: .ini, .cfg, .conf, .properties, .config, .plist, .xsd, .wsdl, .avsc, .prisma, plus project and configuration files recognized by name.

Other text sources in the corpus, including the languages and extensions listed above, are searchable too. The syntax parser catalogue alone does not determine which files can be indexed: the RAG corpus has its own customizable selection of extensions and filenames.

Extractors for office documents and PDF

  • Word — .docx: text from the main document’s paragraphs, for finding written decisions and requirements.
  • Excel — .xlsx: cell values with worksheet names and cell addresses. Stored values are used, or formula text when no value is available; the workbook is not recalculated.
  • PowerPoint — .pptx: slide text in presentation order, with slide numbers.
  • PDF — .pdf: existing text extracted through Poppler’s pdftotext. Image-only scans need OCR beforehand; this extractor does not perform OCR.

Document indexing is the foundation of the knowledge base: it covers the knowledge and data in the configured corpus, not just code documentation. Text, Markdown, office documents and structured data form one searchable collection of sources. Several people and agents can query the same instance and retrieve the same references without copying the knowledge base into every conversation.

Specialized parsers enrich that foundation: JSON and JSONC can be split around top-level keys, while compatible parsers cover formats such as YAML and TOML. Without a syntax parser, readable text uses standard text chunking. Code parsing is an additional capability of this document knowledge base, not a requirement for adding knowledge to it.

Extracted text participates in literal and semantic retrieval alongside the other project sources. Document embeddings are selected separately from code embeddings, so reports and specifications can use a profile suited to their language. When extraction is unavailable or fails, the file remains represented by metadata.

Document extraction has been available since 0.6.6 and is included in 0.9.9. PDF extraction requires Poppler on the server host. Configured extensions, corpus exclusions and size limits apply. Supported formats and usage guide.
